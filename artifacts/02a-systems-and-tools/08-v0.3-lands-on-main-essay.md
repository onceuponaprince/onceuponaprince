# The Landing Tax

*For two days v0.3 existed as branches. It became real in one hour. The building was never the expensive part.*

I want to lead with the conclusion, because the whole point is that the order is backwards. The forty commits were the cheap part. The hour I spent merging them onto one main, gating them, and pushing was the part that decided whether any of it was true. We talk about software as if it is built when it is written. It is not. It is built when it lands.

Here is the shape of the last forty-eight hours, factually. The v0.3 of my agent stack went from a scatter of parallel branches to one consolidated `origin/main`. Roughly forty `feat(spore-*)` commits, numbered v0.3 #1 through #13. A LocalModelTriager. Adaptive tool ranking from telemetry. An in-process port of the graph layer. A WASM plugin loader. MCP over SSE. A deterministic classifier engine. Three merged PRs, #26, #28, #32. Five `impl/w-*` worktrees, each holding one slice, plus a `feat/v0.3-remaining-build` branch holding more. By every dashboard that counts commits, that is a productive two days. By the only measure that matters, it had produced nothing yet.

## 1. Forty commits and nowhere to stand

The consensus model of throughput is the one I was running on without noticing. Parallelise. One worktree per slice, one agent per worktree, contract-frozen, dispatched. The handoff-board pattern I built two scenes ago is good, and it did its job: five slices moved at once instead of in series. The instinct that follows is the one to interrogate. *More worktrees, more speed.* It is solid. It is also, in the specific sense that matters, false.

It is false because a branch is not a shipped thing. It is a claim that a thing could ship. Five branches off the same base, all touching the same Rust workspace, are five unverified claims that have not yet been asked to agree with each other. The commit count says forty. The number of those commits that had survived contact with the others, on a trunk, under a test suite, was zero. I had a productive dashboard and nothing I would put my name to.

## 2. Branches are inventory

The right frame for this is not from software. It is from a factory floor.

Lean manufacturing has a precise and unsentimental view of work that is started but not integrated. It is called work-in-process inventory, and the Toyota Production System treats it as a liability, not an asset. A half-built thing on a shelf is not progress banked. It is capital frozen, risk accumulating, and a defect you have not found yet, because the thing it has to fit into has not arrived. Inventory is waste until it flows. The discipline is not to maximise parts produced. It is to minimise the parts sitting between stations.

A feature branch is work-in-process inventory. It looks like progress because the commits are real. But until it flows into the trunk it is frozen capital with an undiscovered defect rate, and the longer it sits the more the trunk drifts underneath it and the more expensive the eventual merge becomes. My local `main` was twelve commits behind `origin/main` before I started. Five worktrees were diverging from a base that was itself stale. That is not five units of progress. That is five integration debts compounding while I admired the commit graph.

So I did the boring, correct thing first: predicted the merges before making them. `git merge-tree`, non-destructive, against every branch. Four clean, two conflicting on exactly one file. That prediction is the equivalent of counting your inventory before you promise a delivery date. It cost two minutes and it told me the consolidation was a small job wearing a large job's clothes. Four merged clean. One had a trivial import-union conflict. The last, the remaining-build branch, merged clean precisely because it had already absorbed the others. The mess I was bracing for was mostly the mess of not having looked.

## 3. The gate is the first true thing

Then the part that earns the essay. I ran the full suite on the merged trunk. `cargo test --workspace`: 409 passed, one ignored, zero failed, zero compile errors. And `pytest` failed exactly once, on a test double that still expected an old typing call my own fix from the same session had replaced. The gate I had just built caught me with the same hand it was built to catch the model with.

This is the thing nobody puts on the throughput dashboard. None of those forty commits had been true until this moment, because true is not a property a commit has. It is a property the trunk has, under a gate, after the parts are asked to agree. The deterministic classifier and the WASM loader and the SSE transport did not become real when they were written. They became real when 409 tests said they still worked sitting next to each other. The defect the suite caught was not in any one branch. It was in the seam, which is the only place defects of that kind can live, and the only place a branch can never show you.

The worst bug of the entire session lived here too. A few hours earlier the fanout pipeline had been confidently fabricating answers because the input was being silently truncated, and it had been doing so under a green status. (I wrote that one up separately. It deserved its own essay.) The relevant point for this one: that bug was only catchable on the consolidated, instrumented trunk. On a branch, in isolation, with a one-word test prompt, it passed. The landing is not where you tidy up after the truth. The landing is where the truth first has somewhere to happen.

## 4. The landing tax

So here is the name, because the thing needs one to be pointed at. The landing tax: the irreducible cost of turning parallel work-in-process into one trunk you can stand on, paid in merge, gate, reconcile, and push, and always larger than the building it follows.

The tax is not overhead. Overhead is work that produces nothing. This produces the only thing that was ever the point. The mistake is filing it under cleanup, scheduling it as an afterthought, and then being surprised when the afterthought is where the bug was. I paid it deliberately this time. Infra fixes committed on their own so they could not be lost in someone else's churn. The unrelated work-in-process snapshotted as its own explicit commit so two bodies of work could not entangle. Conflicts predicted before they were created. The suite run before the push, not after. Worktrees and spent branches removed, the remote pruned, the trunk reconciled to zero divergence. No broken intermediate state at any point, because a broken intermediate state is just inventory that has caught fire.

Count commits and you will optimise for branches. Count trunks you would sign your name to and you will optimise for the only number that was ever real. v0.3 was not built over two days. It was built in the hour it stopped being branches. Everything before that was just parts on a shelf, and a shelf is not a product.
